# Архітектура персонального Second Brain

Цей документ описує системну архітектуру локальної персональної бази знань (Second Brain) для студента, спроєктованої за принципами **Local-first**, **Zero Vendor Lock-in** та моделі організації **PARA**.

---

## 1. Загальні принципи та цілі системи

1. **Повна автономність (100% Offline):** Робота без доступу до зовнішніх хмарних бекендів, API чи пропрієтарних сервісів.
2. **Відсутність прив'язки до вендора (No Vendor Lock-in):** Базовим джерелом істини (Single Source of Truth) є звичайні файли у форматі CommonMark Markdown (`.md`) з метаданими у форматі YAML Frontmatter.
3. **Висока швидкодія (Sub-millisecond Retrieval):** Для навчальної бази обсягом 500–1000 нотаток усі індекси (повнотекстовий пошук, теги, граф зворотних зв'язків) підтримуються в оперативній пам'яті (In-Memory).
4. **Прозоре версіонування:** Автоматичне фіксування історії змін через локальний Git-репозиторій без сторонніх хмар.
5. **Інтеграція з Agent Skill:** Інтелектуальна обробка нотаток (сортування Inbox, витяг тегів, зв'язування) делегується робочому простору Antigravity Agent Skill.

---

## 2. Модель організації даних (PARA)

Файлова система розділена на п'ять кореневих директорій усередині `notes/`:

```text
notes/
├── 00_Inbox/        # Вхідна черга: необроблені конспекти, сирі думки, чернетки
├── 01_Projects/     # Поточні навчальні завдання з дедлайнами (лабораторні, курсові, підготовка до сесії)
├── 02_Areas/        # Довгострокові дисципліни та сфери знань (наприклад: "Спеціалізовані КС", "ОС")
├── 03_Resources/    # Довідкові матеріали, шпаргалки, специфікації ISA, алгоритми, формули
└── 04_Archives/     # Завершені дисципліни, здані лабораторні минулих семестрів
```

### Життєвий цикл нотатки:
1. **Створення:** Нова нотатка потрапляє в `00_Inbox/` зі статусом `status: "inbox"`.
2. **Обробка (Triage):** Користувач або Agent Skill структурує конспект, додає теги й переміщує його:
   * у `01_Projects/` (якщо це частина поточного проєкту або лабораторної);
   * у `02_Areas/` або `03_Resources/` (якщо це постійний концепт або довідник).
3. **Завершення:** Після завершення семестру/захисту проєкти переносяться в `04_Archives/` зі зміною статусу на `status: "archived"`.

## 3. Специфікація моделі нотатки

Кожна нотатка є текстовим файлом `.md` із суворим заголовком YAML Frontmatter:

```yaml
---
title: "Назва теми українською"
created: "2026-11-22T14:41:38+02:00"
updated: "2026-11-22T15:10:00+02:00"
tags:
  - архітектура-кс
  - апаратне-прискорення
status: "active"      # inbox | active | archived
type: "concept"       # lecture | lab | concept | resource | moc | project
source: "Лекція 3: Матричні обчислювачі"
---
```

### Синтаксис зв'язків:
* **Внутрішні посилання:** `[[Назва нотатки]]` або `[[відносний/шлях/до/файлу]]`.
* **Математичні вирази:** LaTeX-синтаксис для вбудованих формул (`$...$`) та відокремлених блоків (`$$...$$`).

## 4. Архітектура компонентів бекенда та пошуку

Система працює за монолітною безсерверною або мікро-серверною схемою:

```text
+-------------------------------------------------------------+
|                     Client (Web UI)                         |
|  - Чистий HTML5 / CSS3 / Vanilla ES6+ JS                    |
|  - Marked.js (Markdown -> HTML) + KaTeX (формули)           |
+------------------------------+------------------------------+
                               | HTTP JSON API
+------------------------------v------------------------------+
|                   Node.js Core Service                      |
|  - Router & Static File Server (`node:http`)                |
|  - In-Memory Index Manager (State Singleton):               |
|      * notesMap: Map<id, NoteMetadata>                      |
|      * linkGraph: Map<title, Set<backlinks>>                |
|      * invertedIndex: Map<token, Set<noteId>>               |
|      * tagMap: Map<tag, Set<noteId>>                        |
|  - Git Versioning Wrapper (`node:child_process`)            |
|  - File System Sync (`node:fs/promises`)                    |
+------------------------------+------------------------------+
                               | FS Operations
+------------------------------v------------------------------+
|                  Дискове сховище (`notes/`)                 |
+-------------------------------------------------------------+
```

### In-Memory пошуковий рушій:
1. При запуску сервера сканується вміст `notes/`, парсяться заголовки YAML та виділяються терміни тексту.
2. Створюється інвертований індекс для повнотекстового пошуку за заголовками, тегами та тілом нотаток.
3. Час відповіді на пошуковий запит серед 1000 нотаток становить **< 5 мс**.

---

## 5. Граф двонаправлених посилань (Wikilinks & Backlinks)

1. **Forward Links:** Регулярний вираз витягує всі конструкції `[[...]]` у тексті нотатки `A`.
2. **Backlinks:** Якщо нотатка `A` посилається на `B`, то в метадані нотатки `B` у пам'яті автоматично додається зворотне посилання на `A`.
3. При рендерингу нотатки в інтерфейсі знизу динамічно додається блок:
   ```html
   <div class="backlinks-panel">
     <h3>Зворотні посилання (Backlinks)</h3>
     <!-- Список нотаток, які посилаються на поточну -->
   </div>
   ```

---

## 6. Локальне версіонування через Git

1. Під час старту бекенд виконує перевірку наявності репозиторію (`git rev-parse --is-inside-work-tree`).
2. При створенні, редагуванні або архівуванні нотаток бекенд додає зміни в Git-індекс і створює атомарний комміт з описом виконаної дії:
   ```bash
   git add notes/
   git commit -m "docs(notes): update 'Систолічні матриці в апаратних прискорювачах'"
   ```
3. Помилки чи блокування процесу Git ізолюються і не перешкоджають збереженню файлу на диску.

---

## 7. Безпека локального середовища

* **Захист від Path Traversal:** Усі вхідні шляхи перевіряються функцією `path.resolve`. Доступ за межі кореневої директорії `notes/` суворо блокується з поверненням HTTP 403.
* **Прив'язка до мережі:** Серверний процес прив'язується виключно до адреси `127.0.0.1` (localhost), виключаючи прослуховування зовнішніх мережевих адаптерів.
